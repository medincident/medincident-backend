# Асинхронный CQRS через транзакционный Outbox

## Обзор архитектуры

Запись и чтение разделены физически: команды применяются к доменной схеме
(`domain.*`) в Postgres-базе command-server, а читаются данные из схемы
проекций (`projections.*`) в отдельной Postgres-базе query-server.

Данные между базами передаются через NATS JetStream:

```
command-server → outbox (domain.outbox_events) → publisher-server → NATS → query-server consumer → projections.*
```

Каждый шаг атомарен или идемпотентен: строка в outbox пишется в той же
транзакции, что и доменное изменение; publisher публикует с At-Least-Once
семантикой; consumer применяет события по принципу ON CONFLICT DO NOTHING.

## Publisher

Сервис `publisher-server` читает неопубликованные строки из
`domain.outbox_events` (где `published_at IS NULL`) и публикует их в NATS
JetStream. Чтобы обеспечить единственного активного публикатора при
горизонтальном масштабировании, сервис при старте захватывает
`pg_advisory_lock(7246490831)`. Реплика, не получившая блокировку,
блокируется на вызове `pg_advisory_lock` и становится активным публикатором, как только первая реплика завершает работу и освобождает блокировку.

Триггер публикации — двойной:
- `LISTEN/NOTIFY` на канале `outbox_events` (мгновенное уведомление)
- Опрос каждые 5 секунд как fallback на случай пропущенных уведомлений

После успешного `Publish` сервис проставляет `published_at = NOW()` на
соответствующей строке.

## Consumer (query-server)

Query-server подписывается на NATS JetStream с параметрами:
- **Durable**: именованный постоянный consumer, переживает рестарт
- **AckPolicy**: `AckExplicit` — каждое сообщение подтверждается явно
- **MaxAckPending**: 256 — ограничение параллельного in-flight окна
- **DeliverPolicy**: `DeliverAll` — при первом старте читает с начала стрима
- **MaxDeliver**: -1 — бесконечные повторные попытки
- **AckWait**: 30s — сообщение переотправляется, если не подтверждено за 30 с

Каждое сообщение десериализуется (proto), диспетчеризуется по типу, и
соответствующий метод Projectors записывает данные в `projections.*`.

## Диспетчер и проекторы

`internal/service/query/domain/dispatcher.go` принимает `*eventv1.Envelope`,
десериализует вложенный `any` через `proto.UnmarshalOptions` и передаёт
сообщение в нужный метод `Projectors`.

Каждый метод проектора идемпотентен: вставка использует
`ON CONFLICT (id) DO NOTHING` (или `DO UPDATE SET ...` для обновлений
с учётом версии). Это гарантирует корректность при повторной доставке.

### Обработка ошибок в consumer

| Тип ошибки | Действие |
|---|---|
| `isMalformed` (неизвестный тип, ошибка десериализации) | `Term()` — сообщение отбрасывается навсегда |
| Транзиентная (DB недоступна, timeout) | `NakWithDelay(5s)` — повторная попытка |
| Успех | `Ack()` |

## NATS стрим

Стрим **не создаётся приложением автоматически** — он должен быть
подготовлен администратором до запуска сервисов. Конфигурация стрима:

- **Name**: `medincident_events`
- **Subjects**: `medincident.event.>`
- **Storage**: File
- **Retention**: Limits (или по требованиям проекта)
- **Replicas**: 3 (в production)

## Разделение баз данных

Command-server и query-server используют **физически разные базы данных**
(разные DSN, разные контейнеры в тестах). Command-server никогда не пишет
в `projections.*`; query-server никогда не пишет в `domain.*`.

Интеграционные тесты (`test/integration/orgstructure/`) явно поднимают два
отдельных PostgreSQL контейнера через testcontainers, чтобы подтвердить
физическое разделение схем.
